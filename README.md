# Behest

**A BEAM language where humans state the request and AI writes the code.**

The name comes from "at someone's behest": the human asks, the AI builds.

**Origin:** I asked Claude (Anthropic's AI) what a language on top of OTP should look like if AI writes most of the code. This design is what it proposed; I'm sharing it to get the community's view. Fittingly, the project itself was made the way Behest proposes: a human asked, the AI built.

> Status: design proposal with a runnable [Elixir prototype](prototype/) of the contracts. No compiler yet. Feedback welcome. See [Discussion](#discussion).

## Why

More and more code is written by AI. The hard part is no longer *writing* code. It is *checking* that the code does what we meant.

Natural language is flexible but ambiguous. Formal specifications are precise but heavy. Behest tries to sit in between: a small language where the parts a human must approve are short, explicit and executable, and the implementation underneath can be generated and regenerated by AI.

## The idea in one picture

```
protocol RateLimit                                   ┐
  client -> server : {check, id: ClientId}           │
  server -> client : ok | {error, rate_limited}      │
end                                                  │
                                                     │  CONTRACT
process RateLimiter implements RateLimit as server   │  written or approved
  handle check(id)                                   │  by a human
    effects [time]                                   │
    examples  (limit: 3, window: 1s)                 │
      at 0ms    check(:a) x3  => ok, ok, ok          │
      at 10ms   check(:a)     => error(rate_limited) │
      at 1000ms check(:a)     => ok                  │
    property                                         │
      forall client, window: accepted <= limit       ┘

implementation                                       ┐
  ...                                                ┘  AI-written, regenerable
end
```

The reviewer reads about 20 lines. The compiler guarantees the rest matches.

## How it works

The human never writes the implementation. The human and the AI build the contract together, one concrete question at a time:

1. **The human writes a request and a first contract**, a few examples, and marks anything they know is undecided with `open "empty list: error, or some default?"`.
2. **The build refuses to pass while any `open` remains.** The AI can't guess; it has to ask. The human answers with an example (`median([]) == {:error, :empty}`) and deletes the `open` line.
3. **The check finds gaps the human didn't know about.** The AI writes two different implementations that both pass the contract; if they disagree on some input (say `median([1, 0])` gives 0 in one and 0.5 in the other), that input is a missing example. The AI shows both answers, and the human picks the right one.
4. **Every answer becomes a permanent, executable example or property.** The AI may regenerate the implementation at any time, but it can never break the contract.

People are bad at writing complete specs but good at judging a concrete case, so the human only ever answers "which of these is right?".

## Core features

| Feature | What it gives the reviewer |
| --- | --- |
| **Inline examples and properties** | Intent as executable syntax; the build fails if they fail |
| **`open` items** | The AI can't guess: the build fails until the human answers each open question |
| **Protocols (two-party session types)** | Message mismatches between processes become compile errors |
| **Effects in signatures** | One glance answers "can this touch the network / ETS / clock?" |
| **Supervision as data** | The process tree is a checked declaration, not scattered callbacks |
| **No macros, one way to do things** | Uniform AI output, readable diffs |
| **Plain BEAM underneath** | Compiles to Core Erlang; interoperates with Erlang and Elixir |

## Discussion

The goal right now is to find out whether this is worth building. Questions I'd most like opinions on:

1. Are typed protocols between processes the right place to put the type system's effort on the BEAM?
2. Should this build on Gleam, or start fresh?
3. Elixir-like or ML-like surface syntax?
4. Would you trust AI-written code more if it came with this kind of contract?

Please open an issue or join the thread on the Erlang Forums or Elixir Forum.
