# Behest

**A BEAM language where humans state the request and AI writes the code.**

The name comes from "at someone's behest": the human asks, the AI builds.

**Origin:** I asked Claude (Anthropic's AI) what a language on top of OTP should look like if AI writes most of the code. This design is what it proposed; I'm sharing it to get the community's view. Fittingly, the project itself was made the way Behest proposes: a human asked, the AI built.

> Status: a design proposal for the language, with a runnable [Elixir prototype](prototype/) of the contracts and no compiler yet. The workflow itself can be used today as [Claude skills](skills/) for 15 languages, and a first [experiment](experiment/results/README.md) has measured what it gains and costs. Feedback welcome. See [Discussion](#discussion).

## Why

More and more code is written by AI. The hard part is no longer *writing* code. It is *checking* that the code does what we meant.

Natural language is flexible but ambiguous. Formal specifications are precise but heavy. Behest tries to sit in between: a small language where the parts a human must approve are short, explicit and executable, and the implementation underneath can be generated and regenerated by AI.

## The idea in one picture

```
protocol RateLimit                                   ┐
  client -> server : {check, id: ClientId}           │
  server -> client : ok | {error, rate_limited}      │
end                                                  │
                                                     │  CONTRACT
process RateLimiter implements RateLimit as server   │  written or approved
  handle check(id)                                   │  by a human
    effects [time]                                   │
    examples  (limit: 3, window: 1s)                 │
      at 0ms    check(:a) x3  => ok, ok, ok          │
      at 10ms   check(:a)     => error(rate_limited) │
      at 1000ms check(:a)     => ok                  │
    property                                         │
      forall client, window: accepted <= limit       ┘

implementation                                       ┐
  ...                                                ┘  AI-written, regenerable
end
```

The reviewer reads about 20 lines. The compiler guarantees the rest matches.

### Reading the example

The task in plain English: *"limit each client to 3 requests per second."* That sentence leaves details open, such as what happens to the fourth request and when the count resets. The contract above settles them, line by line:

| Part | What it says |
| --- | --- |
| `protocol RateLimit` | The conversation between the two sides. A client sends `{check, id}`; the server must answer `ok` or `{error, rate_limited}`. Any other message or reply is a compile error. |
| `process RateLimiter ... as server` | A long-running process (a `gen_server` underneath) that plays the server side of that protocol. |
| `handle check(id)` | The code that runs when a `check` message arrives. The body is the AI's job. |
| `effects [time]` | The only side effect allowed is reading the clock. Touching ETS, files or the network is a compile error, so a reviewer sees at a glance what the code can do. |
| `examples (limit: 3, window: 1s)` | Concrete scenarios, run on every build against a virtual clock. At 0 ms client `:a` makes three calls (`x3`) and all succeed. At 10 ms a fourth is **rejected** (not queued or delayed). At 1000 ms a new window has started, so it succeeds again. |
| `property` | A rule that must hold for *any* client and window, checked on random inputs: the number of accepted calls never exceeds the limit. |
| `implementation` | Everything below this line is AI-written and can be regenerated freely. It may use a map, ETS or anything else, as long as the contract holds. If it switches to ETS, it must add `ets` to the effects line, which shows up in the diff as a contract change that needs approval. |

Note the split: the examples say *what should happen in specific cases*, the property says *what must always be true*, and the protocol and effects say *what the code may talk to and do*. Together they leave little room for a wrong implementation to pass.

This is the language as designed. The [prototype](prototype/) already runs the examples, properties and effect checks as an Elixir macro library; protocols and the virtual clock come with the real compiler.

## How it works

The human never writes the implementation. The human and the AI build the contract together, one concrete question at a time:

1. **The human writes a request and a first contract**, a few examples, and marks anything they know is undecided with `open "empty list: error, or some default?"`.
2. **The build refuses to pass while any `open` remains.** The AI can't guess; it has to ask. The human answers with an example (`median([]) == {:error, :empty}`) and deletes the `open` line.
3. **The check finds gaps the human didn't know about.** The AI writes two different implementations that both pass the contract; if they disagree on some input (say `median([1, 0])` gives 0 in one and 0.5 in the other), that input is a missing example. The AI shows both answers, and the human picks the right one.
4. **Every answer becomes a permanent, executable example or property.** The AI may regenerate the implementation at any time, but it can never break the contract.

People are bad at writing complete specs but good at judging a concrete case, so the human only ever answers "which of these is right?".

| Step | Status |
| --- | --- |
| `open` items, examples and properties failing the build | Works in the [prototype](prototype/) |
| Disagreement check between two implementations | Design only; see the [design](docs/design.md) |

See the [walkthrough](docs/walkthrough.md) for a full worked example with real output.

## What trying it showed

The workflow was built as [Claude skills](skills/) and run by AI agents on small tasks, with and without the skills ([results and limits](experiment/results/README.md)). Four things changed how I see the idea:

- **The gain comes from showing every choice before the code is written.** Asking is only part of it. In the runs, about half of the unusual things the human wanted were caught in a plain list of "I will also assume, unless you object", not by a question. So the skills now sort open points into a few questions and a list of defaults, each with a proposal, in one message.
- **A plain prompt is already good when the human wants the conventional thing.** It got 63 of 69 decisions right against 69 of 69, at a fifth of the cost. Where the human wants something unusual it delivered the conventional solution, and after a round of corrections still missed the choices it had never mentioned (46 of 52 against 52 of 52).
- **The ceremony has to match the risk.** The skills have three tiers. The light tier (show the choices, write example tests, implement) cost the same agent time as a plain prompt and got 26 of 26.
- **The strongest results so far are on existing code.** Writing contracts for two of my own Elixir libraries found real bugs in both.

These are small runs in which an AI played the human, so they are a first look, not proof. What they do not yet measure is a real person's time and attention.

## Core features

| Feature | What it gives the reviewer |
| --- | --- |
| **Inline examples and properties** | Intent as executable syntax; the build fails if they fail |
| **`open` items** | The AI can't guess: the build fails until the human answers each open question |
| **Protocols (two-party session types)** | Message mismatches between processes become compile errors |
| **Effects in signatures** | One glance answers "can this touch the network / ETS / clock?" |
| **Supervision as data** | The process tree is a checked declaration, not scattered callbacks |
| **No macros, one way to do things** | Uniform AI output, readable diffs |
| **Plain BEAM underneath** | Compiles to Core Erlang; interoperates with Erlang and Elixir |

## Discussion

The goal right now is to find out whether this is worth building. Questions I'd most like opinions on:

1. Are typed protocols between processes the right place to put the type system's effort on the BEAM?
2. Should this build on Gleam, or start fresh?
3. Elixir-like or ML-like surface syntax?
4. Would you trust AI-written code more if it came with this kind of contract?

Please open an issue or join the thread on the Erlang Forums or Elixir Forum.
